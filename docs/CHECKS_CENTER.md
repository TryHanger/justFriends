# Центр проверок проекта

На странице `/standards` вкладка **«Проверки проекта»** показывает пять заранее заданных проверок: pytest, Ruff, Vitest, TypeScript и сборку Vite. Данные берутся из запущенных инструментов. Статус, отдельные тесты и диагностические сообщения сохраняются в таблице `quality_check_runs`; история переживает перезапуск API. Новый запуск получает UUID, сначала имеет состояние `queued`, затем `running` и терминальный статус. При старте API незавершённые запуски отмечаются `interrupted`.

## Локальный запуск

Runner выключен по умолчанию. Для доверенной локальной демонстрации создайте `.env` из `.env.example` и включите его:

```dotenv
ENVIRONMENT=local
QUALITY_RUNNER_ENABLED=true
```

После этого выполните `docker compose up --build -d` и откройте `http://localhost:8080/standards`. Токен вводить не требуется: история, измерения и запуск доступны прямо на локальном сайте. Не публикуйте `.env`. Docker Compose открывает веб-сайт только на `127.0.0.1:8080`. В контейнере API работают pytest и Ruff. Три проверки интерфейса выполняются в отдельном контейнере `frontend-checks` с Node.js; контейнер доступен API только через внутреннюю сеть Docker, не получает доступ к БД и не публикует порт на компьютере. Если он не запущен, интерфейс показывает проверку как недоступную. На локальной машине с установленными зависимостями фронтенда и сервером, запущенным из корня репозитория, также доступны все пять видов проверок.

Чтобы выполнить проверки интерфейса вручную, используйте `npm --prefix frontend ci`, `npm --prefix frontend test`, `npm --prefix frontend run lint`, `npm --prefix frontend run build`. Проверка типов запускается через `tsc -b` по настройке в `frontend/tsconfig.json`.

## Безопасность и данные

API не принимает команд, путей и произвольных аргументов от браузера. Вызовы используют фиксированные аргументы и каталоги, `shell=True` не применяется. Требуются `ENVIRONMENT=local`, флаг включения и служебный заголовок `X-Quality-Local: 1`, который сайт добавляет автоматически. Запросы с посторонних сайтов отклоняются. Дополнительно разрешены только локальные адреса БД или сервис `db` из Compose. Проверки запускаются последовательно, с ограничением времени; при таймауте завершается дерево процессов. Вывод хранится максимум до 12 000 символов, отдельное сообщение теста — до 2 000. Известные секреты из переменных окружения и выражения вида `token=...` маскируются. Тестовый процесс получает временную SQLite БД, пустой API-ключ и автономный NLP backend.

Обычная CORS-конфигурация разрешает Vite на локальных адресах. Nginx проксирует `/api/` и не передаёт runner наружу через отдельный порт. Внутренний контейнер принимает только три фиксированных ID через изолированную сеть Docker; он запускает инструменты без shell и с ограничением времени. Локальный адрес сам по себе не включает runner: нужен явный флаг и служебный заголовок. Это локальный учебный инструмент, его нельзя включать на staging или production. Предполагается один процесс API. При нескольких worker-процессах блокировка одновременных запусков не глобальная.

Приложение по существующей архитектуре создаёт отсутствующие таблицы через SQLAlchemy `create_all` при локальном старте. Для существующих БД предусмотрены **добавочные** SQL-файлы в `migrations/` для SQLite и PostgreSQL; применять их вручную следует только после проверки адреса локальной БД и резервной копии. Никаких миграций на удалённых БД этот этап не выполняет.

## API

- `GET /api/v1/standards/checks` — реестр и доступность инструментов.
- `POST /api/v1/standards/checks/{check_id}/runs` — создать запуск (202).
- `GET /api/v1/standards/checks/runs/{id}` — статус и детали.
- `GET /api/v1/standards/checks/runs/history?check_id=&status=` — сохранённая история с фильтрами.
- `GET /api/v1/standards/checks/runs/{first_id}/compare/{second_id}` — сравнение одинаковых видов проверок.

Кроме чтения реестра, запросы требуют автоматически добавляемый сайтом заголовок `X-Quality-Local: 1`. Старый `POST /standards/quality/run` сохранён для совместимости с тем же локальным ограничением.

## Связь со стандартами и пределы вывода

Каталог содержит ссылки на ISO/IEC 25010:2023 (модель качества), ISO/IEC 25023:2016 (меры качества продукта), ISO/IEC/IEEE 29148:2018 (инженерия требований) и ISO/IEC/IEEE 29119-3:2021 (документация тестирования). Каждая проверка показывает своё требование проекта, инструмент, фактический результат и обоснованную характеристику качества. Запуск тестов сообщает проверенное поведение выбранных сценариев; статические инструменты проверяют только свои правила; сборка подтверждает сборку артефакта. Эти данные не измеряют все характеристики качества и не подтверждают сертификацию ISO. Порогов или «процента качества» не вводилось.

В разделе **«Качество и тесты»** блок ISO/IEC 25023:2016 автоматически читает последние сохранённые запуски и выводит четыре проектных показателя: долю успешных выполненных серверных тестов, такую же долю для интерфейса, число замечаний Ruff и число ошибок TypeScript. Для тестовых долей знаменатель — только выполненные тесты; пропущенные указаны отдельно. Карточки показывают изменение относительно предыдущего запуска того же инструмента и позволяют открыть оба исходных результата. Если подходящего результата нет, показывается «нет данных», а не ноль. Девять характеристик ISO/IEC 25010:2023 показаны на русском языке с исходным названием в подсказке; наличие свидетельства означает лишь частичную проверку. Формулы не объявляются дословными мерами ISO; стандарт не задаёт универсальных порогов, а проектные цели пока не утверждены. API: `GET /api/v1/standards/quality/measurements`.

## Сценарий демонстрации

1. Откройте `/standards` и вкладку «Проверки проекта».
2. Покажите список пяти доступных проверок и распределение инструментов между API и отдельным контейнером интерфейса.
3. Запустите **Backend Tests**.
4. Дождитесь перехода из `queued/running` в итоговое состояние; откройте конкретный тест и его сообщение.
5. Обратите внимание на тесты некорректных входных данных в `tests/test_nlp_api.py` и `tests/test_upload_validation.py`: они проверяются без изменения бизнес-логики.
6. Запустите проверку второй раз, откройте историю и сравните оба реальных запуска. При отсутствии двух записей сравнение недоступно.
7. Запустите Vitest, проверку типов и сборку интерфейса и откройте их реальные результаты.
8. Покажите связь с каталогом ISO и перечень качеств, которые ещё не оценены в соседней вкладке.
9. В разделе «Качество и тесты» покажите запуск pytest, результаты отдельных тестов, частичные свидетельства по характеристикам, динамику ISO/IEC 25023:2016 и исходные записи. Поясните формулу, пропуски и границы вывода для каждого показателя.
